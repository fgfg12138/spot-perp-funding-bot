# 执行协议：AI-Agent 流水线式项目管理方案

> **用途**：这个文件定义了"如何让 AI 在不偏离计划、不丢失上下文的前提下，分阶段完成大型项目"。  
> **适用场景**：用户单次消息要求执行多步骤、跨文件、需测试验证的复杂任务。  
> **核心思路**：以磁盘文件为"持久化上下文"，以 plan.md 为"当前阶段契约"，以 CI 为"质量门禁"。

---

## 1. 核心问题

AI 的上下文窗口限制了单次对话能承载的信息量。对于 P0-P4 这样 50+ 小时的项目，不能指望一次全部搞定。

**解决思路**：分阶段执行，每个阶段由 plan.md 锁定范围，通过磁盘文件传递状态，避免上下文膨胀导致的"遗忘"和"偏离"。

---

## 2. 执行模型

```
┌─────────────────────────────────────────────────────┐
│                Phase 0: 初始化 / 定锚                │
│  1. 读 AGENTS.md + 项目上下文                        │
│  2. 写 plan.md — 锁定当前阶段的范围和任务列表         │
│  3. 跑 CI 确认起点全绿                                │
│  4. 写 MEMORY.md + 更新 AGENTS.md (项目状态)         │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│             Phase 1: 实现 + 修改 + 测试               │
│  ┌────────┐  ┌────────┐  ┌──────────┐  ┌──────────┐ │
│  │ 读文件  │→ │ 改代码  │→ │ 跑 vtest  │→ │ 跑 tsc   │ │
│  └────────┘  └────────┘  └──────────┘  └──────────┘ │
│                    │         │                       │
│               ┌────┴─────────┴────┐                  │
│               │     全部通过?      │                  │
│               └────┬─────────┬────┘                  │
│                  no│         │yes                    │
│              ┌─────┘         └─────┐                 │
│              ▼                      ▼                 │
│         修复再跑              Phase 2                 │
└──────────────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│          Phase 2: 验证 + 记录 + 提交 / 下阶段          │
│  1. 确认 CI 全绿                                      │
│  2. 更新 overview.md (当前进度)                        │
│  3. 写 MEMORY.md (关键决策和技术债务)                   │
│  4. 生成下一个 plan.md (如果还有剩余阶段)               │
│  5. 如有必要，更新 AGENTS.md 中的项目状态               │
│  6. 等待用户确认 → 进入下个阶段                          │
└─────────────────────────────────────────────────────┘
```

## 3. 关键文件协议（三文件系统）

### 3.1 `plan.md` — 当前阶段契约

> **位置**：项目根目录 `docs/plan-{阶段名}.md`  
> **生命周期**：Phase 0 创建，Phase 2 归档  
> **内容**：

```markdown
# Phase: {名称} (如 P0-OKX-Adapter)

## 范围
- 精确描述这个阶段要做什么 / 不做什么

## 任务列表
1. [ ] 具体任务 1 — 涉及文件列表
2. [ ] 具体任务 2 — 涉及文件列表
   ...

## 质量标准
- 所有 vitest 测试通过
- tsc --noEmit 零错误
- 无新引入的 `as any` / 空 `catch {}`
- 函数 ≤ 60 行（除非有充分理由）

## 确认门禁
- [ ] CI 全绿
- [ ] 代码已自审
- [ ] READ_ONLY/SHADOW 模式安全不受影响
```

### 3.2 `MEMORY.md` — 项目持久记忆

> **位置**：`.workbuddy/memory/MEMORY.md`  
> **生命周期**：持续增长，从不清空  
> **内容**：
- 已完成的关键变更
- 技术决策和理由
- 已知的技术债务和待办
- 跨阶段需要记住的约定

### 3.3 `AGENTS.md` — 项目指南（更新项目状态部分）

> **位置**：项目根目录  
> **只更新**：`Current Project Baseline` 部分中的状态描述和完成度估计

## 4. 阶段切分策略（针对本项目的 46-54 小时工作）

### 建议的切分粒度

| 粒度 | 适用场景 | 工作量 |
|------|---------|--------|
| **小阶段** | 单一文件改动 + 配套测试 | 1-3 小时 |
| **中阶段** | 一个完整 adapter 的实现 | 3-5 小时 |
| **大阶段** | 整个 P 里程碑 | 8-12 小时 |

### 推荐分法（12 个阶段）

```
Phase 1:  accountTypes.ts — IAccountAdapter 下单方法去掉 optional    → ~30 分钟
Phase 2:  OKX adapter 实现 submitOrderLeg                                → ~4 小时
Phase 3:  OKX adapter 实现 fetchOrderByClientOrderId + validateOrderPlan → ~2 小时
Phase 4:  OKX adapter 实现 transferInternal                               → ~2 小时
Phase 5:  HTX adapter 实现 submitOrderLeg                                → ~4 小时
Phase 6:  HTX adapter 实现 fetchOrderByClientOrderId + transferInternal  → ~3 小时
Phase 7:  HTX fetchOpenOrders 修复 + 符号映射                           → ~2 小时
Phase 8:  preOrderExecutionGate + safeExecutionOrchestrator 解硬编码     → ~2 小时
Phase 9:  finalPreExecutionAudit 可配置化                                 → ~1 小时
Phase 10: Worker 执行链路集成 (开仓)                                      → ~5 小时
Phase 11: Worker 平仓逻辑 + 风控检查                                       → ~5 小时
Phase 12: 测试补全 (单元 + 集成 + 安全门)                                 → ~6 小时
        ≈ 36-40 小时 (不含 P5 运维)
```

## 5. 如何保证"不偏离计划"

### 5.1 plan.md 是硬约束

- Phase 0 写完 plan.md 后，**所有改动必须对应 plan.md 中的任务**
- 如果实现过程中发现新问题，**先记到 MEMORY.md 的技术债务部分**，不在当前阶段解决
- 除非新问题阻塞了当前阶段，否则不做 scope creep

### 5.2 改动前先读

每次修改文件前，先读一遍它的当前内容。任何偏离 plan.md 的修改在读文件环节就会被发现。

### 5.3 CI 是质量门

- 每个阶段结束前，必须跑 `npx vitest run lib/strategy-v121` + `npx tsc --noEmit -p tsconfig.ci.json`
- 不通过就不结束当前阶段。不允许"先提交再修"。

### 5.4 用户确认是阶段门

- 每个阶段结束后，Phase 2 生成下一个 plan.md
- **等待用户说"继续"**，才进入下一个 phase
- 用户可以在任何阶段结束后选择暂停、调整方向、或退出

## 6. 如何避免上下文丢失

### 6.1 每轮重启的冷启动流程

当你（AI）在新对话中冷启动时：

```
1. 读 AGENTS.md                     → 理解项目身份和战略目标
2. 读 docs/execution-protocol.md     → 了解执行协议
3. 读 docs/plan-当前阶段.md          → 了解当前在做什么
4. 读 .workbuddy/memory/MEMORY.md    → 了解已完成的决策和历史
5. 读 .workbuddy/memory/YYYY-MM-DD.md → 了解最近一次工作内容
6. 跑 CI 确认起点                    → 确保没有已损坏的状态
7. 开始实现
```

### 6.2 每个阶段结束后必须写

- `overview.md` — 当前进度（已完成/进行中/待开始）
- `MEMORY.md` — 关键决策、技术债务、新发现
- `docs/plan-下阶段.md` — 下一个阶段的 plan

### 6.3 禁止依赖"AI 记得"

任何需要跨阶段保留的信息，**必须写入磁盘文件**。包括：
- OKX 的 API 签名方式与 Binance 不同
- HTX 的交易对符号是小写的
- 某个文件有哪些历史遗留问题需要注意
- 你（用户）的偏好和决策

---

## 7. 故障恢复协议

如果某个阶段中途中断（AI 超时、断网、手动停止）：

### 恢复流程

```
1. AI 冷启动
2. 读 plan.md 看当前阶段的任务
3. 跑 CI 看代码是否干净
4. 读最近改动的文件，手动检查是否已部分完成
5. 更新 plan.md (把已完成的打勾，未完成的保留)
6. 继续执行
```

### 破坏性操作保护

- 禁止直接删除文件（用 `git checkout` 回退）
- 每个阶段开始前，AI 检查 `git status`，确保没有未提交的混乱状态
- 如果改动已经完成但 CI 未跑完 → 先跑 CI，再决定是继续还是回退

---

## 8. 你的角色（用户的职责）

1. **说"继续"** — 每个阶段结束后，你说一句"继续"或"下个阶段"，AI 进入下一个 Phase
2. **必要时说"停"** — 如果发现方向不对，随时说"停"，AI 会停下来调整 plan
3. **提供 OKX/HTX API Key** — 实盘需要 API 密钥，按模式分阶段提供
4. **审核 plan.md** — 每个 Phase 0 生成的 plan.md，你可以先看一眼再确认执行

---

## 9. 一句话总结

**你写 plan.md → 我执行 + 测试 → 我写 MEMORY.md + 下一个 plan.md → 你说"继续" → 循环直到做完**

就这么简单。每次只做一个阶段，每个阶段都有明确的契约和质量门禁，不会跑偏。
